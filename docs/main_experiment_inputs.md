# Inputs for the five main experiments

The five groups are 14B handwritten, 14B induced, 14B self-play, 8B handwritten, and 8B induced.
Self-play has two rounds, so these groups correspond to six training arms: A2–A7.

See [data contents](data.md) for the bundled questions, index, demonstrations, codebooks,
and preference files. Model weights and the raw collection pools below are separate.

## Shared inputs

| Input | Contents | Needed for |
| --- | --- | --- |
| Training questions | The fixed 465-question split; `id`, `question`, and reference `answer` | Collection, outcome grading, and candidate checks |
| Test questions | The fixed 166-question split with the same fields | Evaluation of all arms, three samples per question |
| Retrieval corpus | Parent documents with stable `docid`, `text`, and optional `title` | Building the shared retrieval index |
| Retrieval index | BM25 files, parent and chunk text stores, and the index manifest | Collection and evaluation; can be generated from the corpus |
| Handwritten codebook | The full trigger, hint, and criterion of the three handwritten rules | A2 and A6 |
| Merged 14B π0 | Complete model weights, model configuration, tokenizer, and chat template | Starting policy and reference for A2, A3, and A4 |
| Merged 8B π0 | The corresponding complete 8B model and tokenizer files | Starting policy and reference for A6 and A7 |

The model artifacts are runtime dependencies, listed alongside data for completeness. The
current code loads tokenizer resources through `models.base_14b` and `models.base_8b`.
These entries must resolve to the matching tokenizer resources; base-model weights are
needed separately only when rebuilding the warm starts.

The reference answers are consumed by outcome grading and programmatic candidate checks.
They do not enter policy, diagnosis, reader, reassignment, repair, or validator prompts.

## Four collection pools

Each pool contains `trajectories.jsonl` and `verdicts.jsonl`. The code selects failed
trajectories from these records; the pool files contain the complete collection.

| Pool under `<output_root>/pools/` | Sampling policy | Samples per training question | Consumers |
| --- | --- | --- | --- |
| `pi0_14b_1` | 14B π0 | 1 | A2 and A3 |
| `pi0_8b_1` | 8B π0 | 1 | A6 and A7 |
| `pi0_14b_4` | 14B π0 | 4 | A4, self-play round 1 |
| `round1_14b_4` | A4's trained policy | 4 fresh samples | A5, self-play round 2 |

Preserve question/sample identifiers, the final answer and status, and each turn's original
system/user input, completion, action, tool observation, forced-finish flag, and execution
status. Judge records must distinguish an incorrect answer from a grading failure.

These pools can be generated by the collection and judge stages. Supplying them allows the
corresponding later stages to reuse a fixed collection. A5 requires new failures from A4's
trained policy.

## Three codebooks

| Codebook | Contents | Consumers |
| --- | --- | --- |
| Handwritten | Three rules: `query-churn`, `search-without-read`, `over-specified-query` | A2 and A6 |
| 14B induced | The frozen 25-rule paper codebook, with stable IDs and full text | A3, A4, A5 |
| 8B induced | The independently induced 14-rule paper codebook | A7 |

All rules need `id`, `trigger`, `hint`, and `criterion`. A list of rubric names alone is
insufficient. The 14B and 8B induction stages can generate their own codebooks from the
corresponding failure pools. Fixed paper codebooks are needed when reproducing the exact
codebook selection instead of running a new induction.

New induction writes codebooks to:

- `<output_root>/A3/induce/codebook.json`
- `<output_root>/A7/induce/codebook.json`

A4 and A5 read A3's codebook without changing it. When no generated codebook exists,
the corresponding fixed codebook is read from `data/codebooks/`.

## Six preference datasets

| Group | Arm | Training data | Starting model / reference |
| --- | --- | --- | --- |
| 14B handwritten | A2 | `data/pairs/A2.jsonl.gz` | 14B π0 |
| 14B induced | A3 | `data/pairs/A3.jsonl.gz` | 14B π0 |
| 14B self-play, round 1 | A4 | `data/pairs/A4.jsonl.gz` | 14B π0 |
| 14B self-play, round 2 | A5 | `data/pairs/A5.jsonl.gz` | A4's trained policy |
| 8B handwritten | A6 | `data/pairs/A6.jsonl.gz` | 8B π0 |
| 8B induced | A7 | `data/pairs/A7.jsonl.gz` | 8B π0 |

Each supplied pair contains its original system/user prompt, chosen and rejected completions,
question ID, and rubric ID. The training prompt
does not contain rubric guidance. Completions include reasoning, state update, and action.
The trainer constructs the masks and appends a supervised EOS; precomputed masks are not required.

The supplied pairs permit direct preference training without repeating collection, induction,
or repair. Training applies whole-pair length filtering. A newly generated pair file under
`<output_root>/<arm>/repair/` takes precedence over the supplied file.
The two self-play rounds have separate datasets.

## Conditional and intermediate inputs

Rebuilding π0 additionally requires the 199-question warm-start split and the complete SFT
demonstrations from BrowseComp-Plus, patents, web, and web_simple. Each SFT sample must retain
its dataset and question identity, original input, and complete target turn. Starting from
the merged π0 models does not require retraining these warm starts.

For continuation from an intermediate stage, retain that stage's inputs and manifests:

- Diagnosis findings for A3/A7 codebook induction.
- Per-arm assignments identifying `(trajectory_id, turn, rubric_id)`.
- Candidate and validator records, plus accepted repairs before length filtering.
- Configuration and input fingerprints, index metadata, and the corresponding model identity.

Full optimizer checkpoints are needed only for resuming an interrupted training run. A5
needs A4's complete exported model even when its round-2 pairs are supplied in advance.

For training and evaluation from ready-made pairs, the minimal input bundle is the six
preference datasets, the two merged π0 models with tokenizer resources, the shared test
questions and answers, and the retrieval index with document stores. A4's trained model
is produced before training A5.
